          DEBOUNCE

          Chờ ngừng thao tác rồi mới chạy. Như thang máy chờ đến khi không còn người bước vào. Dùng cho ô tìm kiếm, validate form, autosave.

          THROTTLE

          Chạy tối đa một lần mỗi khoảng thời gian. Như súng bắn theo nhịp, dù giữ cò liên tục. Dùng cho scroll, resize, kéo thả.

          Bấm Giả lập gõ: debounce chỉ chạy sau mỗi quãng dừng. Bấm Giả lập scroll: debounce chỉ chạy một lần ở cuối, còn throttle chạy đều, nên throttle hợp với việc cần cập nhật liên tục trong lúc thao tác. Demo chạy ngay trên slide.

          Lỗi 1: tạo debounce trong thân component

          SAI: MỖI LẦN RENDER MỘT TIMER MỚI 
          function Search() {
  const [q, setQ] = useState('');
  const search = debounce(callApi, 300);

  return (
    <input value={q} onChange={(e) => {
      setQ(e.target.value); // gây re-render
      search(e.target.value);
    }} />
  );
}
// Gõ 5 ký tự: vẫn gọi API 5 lần, chỉ là trễ hơn
          ĐÚNG: GIỮ INSTANCE ỔN ĐỊNH, HỦY KHI UNMOUNT 
          function useDebounced(fn, delay) {
  const timer = useRef();
  const latest = useRef(fn);
  useEffect(() => { latest.current = fn; });
  useEffect(() => () => {
    clearTimeout(timer.current);
  }, []);

  return useCallback((...args) => {
    clearTimeout(timer.current);
    timer.current = setTimeout(
      () => latest.current(...args), delay
    );
  }, [delay]);
}
          Liên hệ Chủ đề 2: state đổi thì function component chạy lại, nên biến khai báo trong thân component được tạo mới. Thực tế có thể dùng hook có sẵn như useDebouncedCallback của thư viện use-debounce.

            XSS: JS của kẻ tấn công chạy ngay trong trang của bạn

            LIVEMột bình luận chứa payload. Token dưới đây là dữ liệu giả, chỉ dùng cho demo.
            <div dangerouslySetInnerHTML={{ __html: comment }} />
            <div>{comment}</div>
            Chưa chạy payload.

            React tự escape nội dung trong {value}. Rủi ro nằm ở những chỗ đi vòng qua cơ chế này.

            Bên trái payload chạy thật và đọc được token giả. Bên phải payload chỉ hiện dưới dạng chữ. Payload của demo không gửi gì ra ngoài. Nhấn mạnh: XSS làm được gần như mọi thứ code của bạn làm được.

            Chống XSS từ gốc, vì không có lớp bảo vệ nào tuyệt đối

            Điểm dễ bị tấn côngCách phòng
            dangerouslySetInnerHTML, innerHTMLTránh dùng; nếu bắt buộc thì sanitize bằng DOMPurify
            URL người dùng nhập: href="javascript:..."Chỉ cho phép http: và https:
            Script và package bên thứ baHạn chế dùng, kiểm tra dependency bằng npm audit

<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(comment) }} />
            Khi review code, thấy dangerouslySetInnerHTML là phải hỏi: dữ liệu này đến từ đâu? CSP cũng chính là thứ có thể chặn được demo vừa rồi trong môi trường cấu hình chặt.

            CSRF: mượn trình duyệt của nạn nhân để gửi request

            <!-- Trên evil.example -->
<form
  action="https://bank.example/transfer"
  method="POST">
  <input type="hidden"
    name="to" value="attacker" />
  <input type="hidden"
    name="amount" value="1000000" />
</form>
<script>
  document.forms[0].submit();
</script>
            Kẻ tấn công không đọc được cookie, cũng thường không đọc được response. Họ chỉ cần request được gửi đi với cookie hợp lệ. bank.example chỉ là ví dụ.

            Chống CSRF, và một hiểu lầm cần đính chính

            • Cookie SameSite: set rõ Lax hoặc Strict, đừng dựa vào mặc định của trình duyệt.
            • CSRF token: server kiểm tra giá trị mà trang độc hại không biết.
            • Header Origin: từ chối request đến từ nguồn lạ.
            • Không đổi dữ liệu bằng GET: Lax vẫn gửi cookie khi người dùng bấm link sang site của bạn.
            HIỂU LẦM

            "Đã cấu hình CORS rồi nên an toàn"

            CORS không chống được CSRF. Nó chủ yếu kiểm soát việc JS có được đọc response hay không, còn form ở trên vẫn được gửi đi.

            MIỄN NHIỄM TỰ NHIÊN

            Token gửi qua header Authorization không bị CSRF, vì trình duyệt không tự đính kèm header này.

            Hỏi trước: ai nghĩ CORS chống được CSRF? Điểm Authorization header sẽ là cầu nối sang slide so sánh nơi lưu token.

            Cách nên dùng cho SPA: tách riêng hai token

            ACCESS TOKEN

            Lưu trong memory

            Authorization: Bearer eyJhbGci...

            Không tự gửi kèm nên không bị CSRF. Tải lại trang thì gọi /refresh để lấy token mới.

            REFRESH TOKEN

            Lưu trong cookie HttpOnly

            Set-Cookie: rt=...; HttpOnly; Secure;
  SameSite=Strict; Path=/auth/refresh

            JS không đọc được. Bật rotation: mỗi lần refresh cấp token mới và vô hiệu token cũ.

            BACKEND PHẢI PHỐI HỢP

            Cookie do server set. Nếu FE và API khác site, cần SameSite=None và phải chống CSRF kỹ hơn.

            BFF: BACKEND FOR FRONTEND

            Token nằm hẳn ở server, trình duyệt chỉ giữ session cookie. An toàn hơn nhưng phức tạp hơn.

            Đây là một cách phổ biến, không phải đáp án duy nhất. Khi đi làm, hãy hỏi team đang dùng cách nào và vì sao. Với BFF chỉ cần nhớ tên.

            Luồng khi access token hết hạn

            Đi từng bước. Bước cuối là nhánh thất bại: nếu refresh token cũng hết hạn thì chuyển về trang login.

            Bốn lỗi hay gặp với luồng refresh

            NHIỀU REQUEST CÙNG NHẬN 401

            Chỉ refresh một lần, các request còn lại chờ kết quả. Nếu không, rotation có thể làm người dùng bị đăng xuất.

            let refreshing = null;

function refreshOnce() {
  refreshing ??= callRefreshApi()
    .finally(() => { refreshing = null; });
  return refreshing;
}
            VÒNG LẶP VÔ HẠN

            Nếu chính /refresh trả về 401 thì không được refresh tiếp.

            LOGOUT CHỈ Ở PHÍA CLIENT

            Cần gọi server để thu hồi refresh token, không chỉ xóa state.

            LỘ TOKEN

            Không ghi token vào log hoặc đưa lên URL.
