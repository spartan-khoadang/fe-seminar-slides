01

Ecosystem & Architecture

Understand the architecture instead of memorizing a framework.

    13 minutes. Three questions: why frameworks exist, where HTML gets created, and how code travels from your machine to the browser.

    From updating the DOM by hand to describing the UI from state

    THEN: JQUERY, EVERY ACTION UPDATES EVERY PLACE 
    let count = 0;

$('#plus').on('click', () => {
  count++;
  $('#count').text(count);
  $('#badge').text(count);
  $('#total').text(count * price);
});

$('#reset').on('click', () => {
  count = 0;
  $('#count').text(count);
  $('#badge').text(count);
  // Forgot #total: the screen is now wrong
});
    Every new action repeats every update. Miss one and the screen is wrong, with no error.
    NOW: REACT, EVERY ACTION ONLY CHANGES STATE 
    function Cart({ price }) {
  const [count, setCount] = useState(0);

  return (
    <>
      <p>{count}</p>
      <Badge value={count} />
      <p>{count * price}</p>
      <Plus onClick={() => setCount(count + 1)} />
      <Reset onClick={() => setCount(0)} />
    </>
  );
}
    Change the state once. Every place on screen follows, so there is nothing to forget.
    Use a shopping cart as the mental picture: count, cart badge, total. The Reset handler on the left forgot one line, and nothing reports an error. On the right, each handler only changes state. Short version: with jQuery you remember to fix the screen, with React you only change the data.

    • Reusable: one ProductCard, used in many places.

    02

    State Management

    The biggest headache, and why Redux is not the answer to everything.

      15 minutes. If you remember one thing from this part: classify state before choosing a tool.

      Prop drilling: passing data through components that do not need it

      AppHolds user
      →
      LayoutUnused, only passes it on
      →
      SidebarUnused, only passes it on
      →
      UserMenuUnused, only passes it on
      →
      AvatarUses user
      HARD TO CHANGE

      Adding one prop means editing the whole chain.

      HARD TO REUSE

      Middle components depend on data they never use.

      HARD TO READ

      You trace through many files to find where data comes from.

      Passing through one or two levels is normal. Prop drilling only becomes a problem when the chain is long and the middle layers are unrelated.

      Solve it in order, and do not jump straight to a global store

      STEP 1

      Put state in the right place

      Move state down near where it is used, or up to the closest common parent.

      <SearchBox />
// keeps its own text
      STEP 2

      Component composition

      Pass the child that already has its data through children.

      <Layout>
  <Avatar user={user} />
</Layout>
      STEP 3

      Context or a store

      When data is truly used in many distant places, like theme or user.

      const user = useContext(
  UserContext
);
      Composition is simple but often overlooked: Layout does not need to know what user is.
      Show the comparison: with composition, the middle layers no longer receive the user prop, and no extra library is needed.

      Composition: put the child in place instead of passing data through

      BEFORE: EVERY LAYER PASSES user
      <Layout user={user} />

function Layout({ user }) {
  return <Sidebar user={user} />;
}
function Sidebar({ user }) {
  return <UserMenu user={user} />;
}
function UserMenu({ user }) {
  return <Avatar user={user} />;
}
      AFTER: APP PLACES Avatar DIRECTLY
      <Layout>
  <Sidebar>
    <UserMenu>
      <Avatar user={user} />
    </UserMenu>
  </Sidebar>
</Layout>

function Layout({ children }) {
  return <main>{children}</main>;
}
      Middle components only leave a slot. If many distant places need the same data, use Context.
      Sidebar and UserMenu are written like Layout: they take children. Analogy: instead of handing a gift from person to person, put it straight into the right box. The outer boxes only hold it.

      Classify state before choosing a tool

      UI / LOCAL

      Needed by one component

      Which modal is open, text in an input.

      useState
      SHARED

      Shared down the tree

      Theme, language. Every consumer re-renders when the value changes.

      Context API
      SERVER

      Data from an API

      Really a copy that may be stale. The most common fresher mistake.

      React Query, SWR
      DERIVED

      Computable from existing state

      Totals, filtered lists. Do not create new state.

      Compute in render
      Once these are separated, very little usually remains for a global store.
      This is the most important slide of this part. Example: a product list from an API is server state, the search box is local, the theme is shared, the filtered count is derived.

      Server state: do not rebuild a cache with useEffect

      BY HAND, AND THIS IS ONLY THE START 
      const [users, setUsers] = useState([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);

useEffect(() => {
  fetch('/api/users')
    .then((r) => r.json())
    .then(setUsers)
    .catch(setError)
    .finally(() => setLoading(false));
}, []);
// Missing: cache, retry, refetch, dedupe
      REACT QUERY 
      const { data, isPending, error } = useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
});
      • Cache: many components share the same data.
      • Dedupe: identical requests are merged.
      • Auto refresh: configurable, when data is stale.
      • Alternatives: SWR, RTK Query.
      Note the code on the left does not check r.ok either. A library is not mandatory, but know what it is doing for you before writing your own.

      Derived state: if you can compute it, do not store it

      WRONG: TWO SOURCES OF TRUTH 
      const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);

useEffect(() => {
  setTotal(items.reduce(sum, 0));
}, [items]);
      RIGHT: COMPUTE DURING RENDER 
      const [items, setItems] = useState([]);

const total = items.reduce(sum, 0);

// Only if it is truly expensive:
// useMemo(() => ..., [items])
      • Left: one extra render, and a moment when total disagrees with items.
      • Right: they can never disagree, and there is less code.
      • Warning sign: a useEffect that only calls setState from other state.
      This comes up constantly in code review. The React docs have a whole article, "You Might Not Need an Effect", linked at the end.

      Global state: choose by project, not by trend

      ModelStrengthsTrade-offs
      Redux ToolkitOne store, actions, reducersClear flow, strong DevTools, large ecosystemMore concepts to learn; RTK cut boilerplate a lot
      ZustandSmall stores through a hookMinimal API, no Provider neededFew conventions, the team sets the structure
      JotaiSmall composable atomsFine-grained re-renders per atomMany scattered atoms can be hard to follow
      Redux is not obsolete: many projects you will join still use it. Understand its data flow and other tools come quickly.
      No need to go deep. The point is that freshers know the options exist and do not judge a codebase for using Redux.
      03

      Web Performance 101

      Measure first, optimize second, and avoid a few common mistakes.

        15 minutes, with two demos: debounce/throttle and DevTools.

        Core Web Vitals: three questions from the user's point of view

        LOADING

        LCP

        Largest Contentful Paint

        How long until the main content appears, like a banner or large text?

        Good: ≤ 2.5 s
        INTERACTIVITY

        INP

        Interaction to Next Paint

        After a click, how long until the UI responds?

        Good: ≤ 200 ms
        STABILITY

        CLS

        Cumulative Layout Shift

        Reading along when an image loads and pushes the text down? Lower is better.

        Good: ≤ 0.1

        Thresholds published by Google, assessed at the 75th percentile of real visits (web.dev/vitals).

        75th percentile means 75% of visits should meet the threshold. Going further: CLS often comes from images without dimensions, or content inserted above what the user is reading.

        Debounce and throttle: both reduce calls, in different ways

        LIVE
        Events
        0
        Debounce
        0
        Throttle
        0

        Both use 300 ms. Each mark is one function call.

        DEBOUNCE

        Wait until activity stops, then run. Like an elevator waiting until nobody else steps in. For search boxes, form validation, autosave.

        THROTTLE

        Run at most once per interval. Like a gun firing at a set rate while you hold the trigger. For scroll, resize, drag.

        Click Simulate typing: debounce runs only after each pause. Click Simulate scroll: debounce runs once at the end while throttle runs steadily, so throttle suits work that must update during the action. The demo runs right on the slide.

        Mistake 1: creating debounce in the component body

        WRONG: A NEW TIMER EVERY RENDER 
        function Search() {
  const [q, setQ] = useState('');
  const search = debounce(callApi, 300);

  return (
    <input value={q} onChange={(e) => {
      setQ(e.target.value); // re-renders
      search(e.target.value);
    }} />
  );
}
// Type 5 chars: still 5 API calls, just later
        RIGHT: STABLE INSTANCE, CLEARED ON UNMOUNT 
        function useDebounced(fn, delay) {
  const timer = useRef();
  const latest = useRef(fn);
  useEffect(() => { latest.current = fn; });
  useEffect(() => () => {
    clearTimeout(timer.current);
  }, []);

  return useCallback((...args) => {
    clearTimeout(timer.current);
    timer.current = setTimeout(
      () => latest.current(...args), delay
    );
  }, [delay]);
}
        When state changes the function component runs again, so variables declared in its body are recreated. In practice you can use a ready-made hook such as useDebouncedCallback from the use-debounce library.

        Mistakes 2 and 3: debounce does not solve everything

        MISTAKE 2: RACE CONDITIONS

        An old response can arrive after a new one. Type re then react, and the re result arrives last and overwrites.

        useEffect(() => {
  const c = new AbortController();
  fetch(url(q), { signal: c.signal })
    .then((r) => r.json())
    .then(setData)
    .catch((e) => {
      if (e.name !== 'AbortError') setError(e);
    });
  return () => c.abort();
}, [q]);
        MISTAKE 3: USING IT TO FIX A SLOW UI

        Debounce only reduces calls. One heavy render is still just as heavy.

        INSTEAD
        • Measure with React Profiler to find the slow part.
        • Reduce re-render scope, place state correctly.
        • Long lists: use virtualization.
        • Heavy computation: split it up or use a Web Worker.
        React Query handles this race for you because results are tied to the queryKey.

        Demo: measure before optimizing, right in DevTools

        NETWORK TAB

        How many requests?

        • Any duplicate requests?
        • Which file is largest?
        • Throttle to Fast 4G to try a slow network.
        LIGHTHOUSE

        Measure page load

        • Reports LCP and CLS.
        • Uses TBT to estimate responsiveness. It does not measure INP.
        • Read the suggestions.
        PERFORMANCE TAB

        Measure interactions

        • Shows live LCP, CLS, INP.

        Security Basics

        XSS, CSRF and token storage, instead of defaulting to localStorage.

          12 minutes. Understand the two attacks first, and the token storage comparison will make sense on its own.

          Why two kinds of token?

          Access tokenRefresh token
          Used toCall APIsGet a new access token
          LifetimeShort, often 5–15 minutesLonger, often days to weeks
          Sent toEvery authenticated APIOnly the refresh endpoint
          If leakedDamage limited to a short windowMore serious, so protect it and make it revocable
          The remaining question: where do we store them? To answer that, we need to understand two attacks.
          Exact lifetimes depend on each system's security requirements. These numbers are only common ranges. Spend just 1 minute here.

          XSS: the attacker's JS runs inside your page

          LIVEA comment containing a payload. The token here is fake, for this demo only.
          <div dangerouslySetInnerHTML={{ __html: comment }} />
          <div>{comment}</div>
          Payload has not run yet.

          React escapes content in {value} automatically. The risk is in whatever bypasses that.

          On the left the payload really runs and reads the fake token. On the right it appears as plain text. The demo payload sends nothing out. Stress this: XSS can do almost anything your own code can do.

          Stop XSS at the source, because no single layer is absolute

          Weak spotDefense
          dangerouslySetInnerHTML, innerHTMLAvoid them; if required, sanitize with DOMPurify
          User-supplied URLs: href="javascript:..."Allow only http: and https:
          Third-party scripts and packagesUse fewer, check dependencies with npm audit
          Whatever slips throughUse CSP to limit which scripts may run
          // User HTML that must be rendered: sanitize first
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(comment) }} />
          In code review, when you see dangerouslySetInnerHTML, ask: where does this data come from? A strict CSP is also what could stop the demo you just saw.

          CSRF: borrowing the victim's browser to send a request

          <!-- On evil.example -->
<form
  action="https://bank.example/transfer"
  method="POST">
  <input type="hidden"
    name="to" value="attacker" />
  <input type="hidden"
    name="amount" value="1000000" />
</form>
<script>
  document.forms[0].submit();
</script>
          The attacker cannot read the cookie, and usually cannot read the response either. They only need the request sent with a valid cookie. bank.example is just an example.

          Stopping CSRF, and a misconception to correct

          • Cookie SameSite: set Lax or Strict explicitly, do not rely on browser defaults.
          • CSRF token: the server checks a value the malicious page cannot know.
          • Origin header: reject requests from unknown origins.
          • No data changes via GET: Lax still sends cookies when a user follows a link to your site.
          MISCONCEPTION

          "We configured CORS, so we are safe"

          CORS does not stop CSRF. It mainly controls whether JS can read the response, and the form above still gets sent.

          NATURALLY IMMUNE

          Tokens sent in the Authorization header are not exposed to CSRF, because browsers do not attach that header automatically.

          Ask first: who thinks CORS prevents CSRF? The Authorization header point bridges to the token storage comparison.

          How do XSS and CSRF differ?

          XSSCSRF
          Where bad code runsIn your pageOn the attacker's page
          What it exploitsThe user's trust in the pageThe server's trust in the browser's cookie
          Can it read data?YesUsually not, it mainly forces actions
          Link to tokensReads any token scripts can reachAbuses automatically sent cookies
          So localStorage avoids CSRF but fears XSS, while an HttpOnly cookie stops XSS reading the token but needs CSRF protection.
          The last sentence leads straight into the next slide.

          Where to store tokens? Each option has a trade-off

          LocationCan XSS read the token?CSRF riskAfter page reload
          localStorageYesNoKept
          sessionStorageYesNoKept, but lost when the tab closes
          In-memory variableHarder, not impossibleNoLost
          HttpOnly cookieNoYes, needs protectionKept
          TRY IT IN THE CONSOLE
          localStorage.getItem('token') // exposed
document.cookie // no HttpOnly cookie here
          No storage is absolutely safe. With XSS, an attacker can still send requests inside the user's session.
          Demo on a local app with an HttpOnly cookie set by the server: open the Console and the Application tab. The cookie shows in the Application tab but not in document.cookie.

          A recommended SPA setup: keep the two tokens apart

          ACCESS TOKEN

          Store in memory

          Authorization: Bearer eyJhbGci...

          Not sent automatically, so not exposed to CSRF. On reload, call /refresh for a new one.

          REFRESH TOKEN

          Store in an HttpOnly cookie

          Set-Cookie: rt=...; HttpOnly; Secure;
  SameSite=Strict; Path=/auth/refresh

          JS cannot read it. Enable rotation: each refresh issues a new token and invalidates the old one.

          THE BACKEND MUST COOPERATE

          The server sets the cookie. If FE and API are cross-site, you need SameSite=None and stronger CSRF protection.

          BFF: BACKEND FOR FRONTEND

          Tokens stay on the server and the browser holds only a session cookie. Safer but more complex.

          This is a common approach, not the only answer. When you start work, ask which approach your team uses and why. For BFF, just remember the name.

          What happens when the access token expires

          Walk through step by step. The last step is the failure branch: if the refresh token has also expired, go to the login page.

          Four common mistakes in the refresh flow

          MANY REQUESTS GET 401 AT ONCE

          Refresh only once and make the others wait. Otherwise rotation can log the user out.

          let refreshing = null;

function refreshOnce() {
  refreshing ??= callRefreshApi()
    .finally(() => { refreshing = null; });
  return refreshing;
}
          INFINITE LOOP

          If /refresh itself returns 401, do not refresh again.

          CLIENT-ONLY LOGOUT

          Call the server to revoke the refresh token, not just clear state.

          LEAKED TOKENS

          Never write tokens to logs or put them in URLs.

          The first mistake often appears only when a page calls many APIs just as the token expires, so it is hard to reproduce. If short on time, move this slide to the self-study material.
